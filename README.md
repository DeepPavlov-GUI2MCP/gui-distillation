## Описание технического решения

### 1. A11Y-only exploration и построение UI-графа LibreOffice Writer (Тетеревлев Р.В.)

Источник данных в A11Y-only подходе — AT-SPI / A11Y Tree. Для каждого UI-узла используются его атрибуты: роль, имя, описание, состояние, координаты, путь родителей и положение во вложенной структуре дерева. Скриншоты в этом подходе не являются источником истины для построения графа, а используются только как вспомогательный артефакт для визуальной проверки состояния.

Перед извлечением действий определяется активная область взаимодействия — `active_root`. Это может быть главное окно, открытое меню, подменю, диалог или overlay. Такой шаг нужен, чтобы не смешивать foreground-контекст, например открытое меню, с фоновыми элементами основного окна.

Далее применяется политика классификации действий. Действия делятся на:
- `macro` — действия, которые могут открыть новый UI-контекст и используются для построения графа;
- `micro` — действия внутри уже открытого контекста, которые не выполняются автоматически как переходы графа, но сохраняются как observation layer.

Для каждого состояния считается A11Y-only signature. Она позволяет определить, изменился ли UI-контекст после выполнения действия и нужно ли создавать новый узел графа. Если действие выполнено и привело к новому состоянию, edge получает статус `confirmed`. Если действие не меняет macro-состояние или отложено политикой безопасности, оно не раздувает граф.

Scheduler использует стратегию BFS: сначала обрабатываются переходы из более близких к root состояний, затем более глубокие уровни. Это обеспечивает равномерное покрытие UI и контролируемое расширение exploration.

Поверх `graph.json` была построена `agent_map.json`. Граф хранит проверенные переходы, а agent map добавляет видимые элементы состояния, scoped observed items и state capabilities.

### 2. VLM-based exploration и построение UI-графов desktop-приложений (Устинов К.)

Источник данных — скриншот текущего состояния приложения; A11Y-дерево не используется как ground truth. Поверх скриншота работает MLLM-teacher (основной — `gpt-5.4`, дополнительно тестировались `gpt-5.4-mini`, `gpt-4.1`, локальный `qwen35-27b` через vLLM), который:
1. описывает текущий экран в семантических терминах (label + NL-описание + список элементов);
2. предлагает следующее действие из словаря атомарных действий.

Pipeline собран из шести шагов: **скриншот → описание через VLM → дедуп состояний по сигнатуре → frontier-список непосещённых действий → выполнение действия → запись узла/перехода в граф**. В отличие от A11Y-подхода, лейблы состояний и имена элементов — семантические (`programming_mode_main`, а не хеш), что делает граф напрямую пригодным как контекст для LLM-генератора задач.

Реализованы несколько exploration-стратегий (`random`, `coverage`, `goal-driven`, `hybrid`) и три раннера: `flat` (последовательный обход), `dfs` (с откатом и перепроходом), `task` (целевой прогон под конкретную задачу). Дедупликация состояний — по комбинации dHash скриншота и семантической сигнатуры от teacher-а. Каждый прогон сохраняется как `state_graph.json` с метаданными (модель, число шагов, экраны, переходы, метрики, usage в токенах и долларах).

Код и финальные графы по приложениям лежат в `vlm-exploration/` (артефакты — в `vlm-exploration/artifacts/state_graphs/`).

## Полученные результаты

### 1. A11Y-only exploration и построение UI-графа LibreOffice Writer (Тетеревлев Р.В.)

#### 1.1. Граф GUI-состояний LibreOffice Writer

Для LibreOffice Writer построен воспроизводимый graph exploration checkpoint:

```text
states / nodes: 42
edges: 41
confirmed: 41
pending: 0
max depth: 3
depth counts: 1 / 11 / 27 / 3
```

В рамках текущей safe macro-policy frontier закрыт: все разрешённые policy переходы выполнены и подтверждены.

Важно: это не означает, что автоматически исследован весь LibreOffice Writer. Потенциально опасные или content-changing действия, такие как Save, Print, Exit, OK, Cancel, Help и dialog checkboxes, намеренно не включались в verified graph и сохранялись только как observed/capabilities в agent map.

#### 1.2. Agent-facing карта

Поверх графа была построена agent-facing карта. Она добавляет к проверенным переходам видимые элементы состояния и возможности интерфейса:

```text
items: 381 (словарь “какие элементы вообще найдены”)
state capabilities: 369 (“что можно видеть или использовать в конкретном состоянии”)
```

`agent_map.json` позволяет агенту понимать, какие элементы видны в текущем состоянии, даже если они не являются проверенными безопасными переходами. Например, в меню File могут быть видны Save и Print, но они остаются observed-only, а не verified transitions.

#### 1.3. Golden set и MLLM-оценка

Дополнительно была подготовлена эталонная разметка UI-элементов для оценки локализации их по скриншоту. На ее основе были протестированы MLLM-модели, предсказывающие bounding boxes элементов интерфейса. Для оценки использовалась метрика IoU. Эти эксперименты стали основой второго направления exploration, где используется визуальный подход через скриншоты и мультимодальные модели.

### 2. VLM-based exploration и построение UI-графов desktop-приложений (Устинов К.)

#### 2.1. Покрытие приложений

Pipeline применён к четырём приложениям: gnome-calculator, gnome-text-editor, eog (image viewer), LibreOffice Writer. Для каждого собран воспроизводимый `state_graph.json` с семантическими лейблами состояний и переходами (артефакты в `vlm-exploration/artifacts/state_graphs/`).

#### 2.2. Сравнение с A11Y там, где оно есть

На gnome-calculator A11Y-дамп использовался как внешний знаменатель для honest coverage:

```text
strict name match:        89.5%
с учётом синонимов:       97.4%
против внешнего GT:       84.6%
```

Единственный устойчивый пропуск — запятая. Содержимое combo-box-ов (~100 валют, единицы измерения и т.п.) pipeline не раскрывает: видит сам селектор и упоминает его в описании, но не скроллит внутри открытого списка.

#### 2.3. Метрика и стоимость прогона

Зафиксировано фундаментальное ограничение: без A11Y-дампа или ручной разметки нет знаменателя для абсолютного coverage — «мы не знаем чего мы не знаем». Поэтому используются относительные дельта-метрики: фиксируется приложение и teacher, меняется pipeline, и сравниваются прогоны между собой. Все правки pipeline в ходе работы стабильно двигали относительное покрытие в нужную сторону. Стоимость одного полного прогона укладывается примерно в $5 на teacher-вызовы.

## Практическая значимость

### 1. A11Y-only exploration и построение UI-графа LibreOffice Writer (Тетеревлев Р.В.)

Полученный A11Y-only граф может использоваться как:
- источник проверенных навигационных переходов по интерфейсу;
- основа для генерации обучающих траекторий;
- база для построения SFT-датасета;
- промежуточное представление интерфейса для Computer-use агента;
- потенциальный MCP-tool или навигационная память для LLM-агента.

В рамках командной работы результаты были использованы для генерации обучающих примеров (сформированы задачи для SFT).

### 2. VLM-based exploration и построение UI-графов desktop-приложений (Устинов К.)

Подход даёт самостоятельный baseline там, где A11Y-подход неприменим или нестабилен:
- платформы без A11Y — Windows, Electron-обёртки, проприетарные UI;
- приложения, где A11Y нестабилен — Impress, VLC, Thunderbird (по результатам скрининга);
- ситуации, когда нужна семантика поверх A11Y — NL-имена и описания, готовые для LLM.

Полученные `state_graph.json` уже сейчас пригодны как контекст для LLM-генератора задач и как baseline для первой версии task-generator-а. В рамках общего проекта это направление дополняет A11Y-only подход и расширяет множество приложений, к которым применимо построение UI-графа.

**Вывод.** PoC успешный: семантический граф собирается, pipeline воспроизводим, базовая стоимость прогона приемлема. Главное, над чем предстоит работать дальше — устойчивая метрика покрытия и дебаг-инструменты; без них подход остаётся PoC-ом. В то же время уже на текущем этапе подход применим там, где A11Y-дерева нет или оно нестабильно.

## Ограничения

### 1. A11Y-only exploration и построение UI-графа LibreOffice Writer (Тетеревлев Р.В.)

У A11Y-only подхода есть ограничения масштабирования:

1. Не все приложения стабильно отдают A11Y Tree.
2. Структура дерева может сильно отличаться между приложениями.
3. Для разных классов UI может требоваться адаптация exploration policy.
4. A11Y Tree не всегда достаточно хорошо отражает визуальные или canvas-зависимые интерфейсы.

Поэтому A11Y-only exploration целесообразно рассматривать как один из компонентов общего GUI2MCP pipeline, дополняемый визуальным exploration через MLLM.

### 2. VLM-based exploration и построение UI-графов desktop-приложений (Устинов К.)

Ограничения текущего состояния VLM-pipeline:

1. Нет устойчивой методики абсолютного coverage на сложных приложениях (Writer и далее) — нет знаменателя.
2. Нет надёжного матчинга VLM↔A11Y имён: синонимы и разный нейминг.
3. Pipeline не раскрывает содержимое прокручиваемых dropdown-ов (combo-box-ы со списками валют, единиц и т.п.).
4. Нет per-state A11Y-снимков для автоматической проверки галлюцинаций teacher-а.
5. Дебаг-инструменты и воспроизводимость прогонов ещё сырые.
6. Метрики прогона — относительные, не абсолютные; корректно сравнивают стратегии при одной модели, но не дают честного «нашли X% приложения».

## Дальнейшие планы

### 1. A11Y-only exploration и построение UI-графа LibreOffice Writer (Тетеревлев Р.В.)

Дальнейшее развитие может идти в нескольких направлениях:

1. Расширить проверку A11Y-only подхода на другие приложения и классы интерфейсов.
2. Улучшить автоматическую адаптацию политики exploration под разные типы A11Y Tree.
3. Сжать граф в более информативное представление: например, векторную или графовую базу знаний.
4. Использовать граф и agent map как MCP-tool для LLM-агента, а не только как источник обучающих данных.

### 2. VLM-based exploration и построение UI-графов desktop-приложений (Устинов К.)

1. Разработать устойчивую методику измерения coverage без A11Y — через ручную разметку или гибрид с A11Y там, где он доступен.
2. Реализовать надёжный матчинг VLM↔A11Y имён для honest-coverage по более широкому набору приложений.
3. Расширить pipeline на работу с прокручиваемыми dropdown-ами и длинными списками.
4. Добавить per-state A11Y-снимки как механизм автоматической верификации описаний teacher-а.
5. Доразвить дебаг-инструменты и воспроизводимость прогонов.
6. Использовать собранные `state_graph.json` как источник трасс для следующего этапа — обучения exploration-политики методами RL.
