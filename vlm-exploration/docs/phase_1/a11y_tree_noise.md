# A11Y Tree: шум в TXT-файлах (INT32_MIN координаты)

## Проблема

В файлах `a11y_buttons.txt`, которые генерирует `parse_xml_to_txt()`, подавляющее большинство строк содержат невалидные координаты:

```
(-2147483648, -2147483648)   (1, 1)
```

Пример из Basic-режима (`a11y_buttons_initial.txt`): **362 строки из 390** имеют такие координаты. Только 28 строк соответствуют реально видимым элементам.

---

## Что означает `-2147483648`

`-2147483648` — это `INT32_MIN` (`−2³¹ = 0x80000000`), сигнальное значение AT-SPI2. Когда GTK-элемент **зарегистрирован в дереве доступности, но физически не отрисован на экране**, `pyatspi` возвращает эту константу как координаты. Размер `(1, 1)` — соответствующий фиктивный размер.

Это не баг в нашем коде — это штатное поведение AT-SPI2: он захватывает **весь граф объектов GTK**, включая скрытые, свёрнутые и не открытые попапы.

---

## Откуда берутся скрытые элементы (Basic-режим)

| Роль | Кол-во | Примеры | Причина скрытости |
|---|---|---|---|
| `menu item` | 325 | Degrees, Radians, Meters, Miles, Parsecs, Light Years… | Пункты всех выпадающих меню конвертера единиц — попапы закрыты |
| `push button` | 10 | New Window, Preferences, Help, About Calculator… | Пункты Primary menu — попап закрыт |
| `radio button` | 9 | Basic, Advanced, Financial, Keyboard | Группа выбора режима — попап закрыт |
| `combo box` | 4 | (безымянные) | Выпадающие списки конвертера — не развёрнуты |
| `label` | 12 | (заголовки меню конвертера) | Скрытые панели |
| `toggle button` | 2 | (элементы управления конвертера) | Скрытые панели |

GNOME Calculator — приложение с несколькими режимами и встроенным конвертером единиц. Все эти элементы существуют в GTK-иерархии постоянно, независимо от режима и состояния UI.

---

## Почему это не ломает клики

`find_button_by_name()` в `a11y_capture.py` содержит явную проверку:

```python
if w > 0 and h > 0 and x >= 0 and y >= 0:
    return x, y, w, h
```

Элементы с `x = -2147483648` не проходят условие `x >= 0` и отбрасываются. На выбор координат для кликов шум не влияет.

---

## Видны ли результаты вычислений в TXT

Частично. В **Programming-режиме** дисплей виден как именованный `label`:

```
label   34₈ = 1C₁₆   (303, 260)   (73, 34)
```

Это результат `7 × 4 = 28`, отображённый одновременно в восьмеричном (34₈) и шестнадцатеричном (1C₁₆) форматах. Также присутствуют метки позиций битов (`15`, `47`).

В **Basic-режиме** дисплей попадает в дерево как безымянный `text`-элемент — имя пустое, текущее число из него не считывается.

---

## Что стоит исправить

Текущий фильтр в `parse_xml_to_txt()`:

```python
if int(w) == 0 and int(h) == 0:
    continue
```

Не ловит случай `(1, 1)` при `x = -2147483648`. Достаточно добавить проверку на отрицательные координаты:

```python
x_int, y_int = int(x), int(y)
if (int(w) == 0 and int(h) == 0) or x_int < 0 or y_int < 0:
    continue
```

Это сократит TXT с 390 до ~28 строк в Basic-режиме и уберёт весь мусор из скрытых меню и попапов, не затронув логику XML и координатный поиск.
